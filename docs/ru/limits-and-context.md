# Лимиты и контекст

[English version](../en/limits-and-context.md) · [README](../../README.md#russian) · [Руководство по использованию](usage-guide.md)

Как Claude Orchestrator решает, сколько работы запускать и на какой модели, когда сохранять своё состояние и во что
обходится работа. Источники: скрипты в `skills/orchestrator/scripts/` (`limits.py`, `costs.py`, `statusline.py`,
`checkpoint.py`), вспомогательный скрипт плагина `scripts/sync_stable.py` и
[`skills/orchestrator/references/limits-and-context.md`](../../skills/orchestrator/references/limits-and-context.md).

Всё работает локально и только на чтение. В скриптах нет сетевого кода: они читают счётчики использования, id моделей,
время и тексты сообщений о лимитах из транскриптов Claude Code и пишут небольшие файлы состояния в
`~/.claude/claude-orchestrator/` (базовый каталог следует за `CLAUDE_CONFIG_DIR`). **Все числа, кроме официальных данных
строки состояния, — оценки.** Значения в примерах ниже условные.

```
 строка состояния (Pro/Max) ──► statusline.json ──┐
 транскрипты всех проектов ───────────────────────┤
 ошибки лимитов, предупреждения «used N%» ────────┼──► limits.py ──► режим · статус моделей · контекст · действия
 limits.json (необязательно) ─────────────────────┘        │
                                                           └──► calibration.json ──► costs.py (≈ % лимитов, бюджеты в %)
```

## Коротко

| Хочу … | Что делать |
|---|---|
| Увидеть текущий режим и его причину | `/orchestrator:limits` |
| Увидеть, кто сколько потратил | `/orchestrator:costs` |
| Получить точные официальные цифры вместо оценок (Pro/Max) | один раз `/orchestrator:setup` — включит [строку состояния](#строка-состояния) |
| Ограничить расход одной задачи | Строка `Budget:` в шапке плана — [Бюджеты планов](#бюджеты-планов) |
| Исправить неверную оценку 5-часового потолка | `session_cap_units` в [`limits.json`](#конфигурация) |
| Пережить `/compact`, `/clear`, перезапуск или сброс лимита | Чекпоинт плана + `/orchestrator:resume` — [Контекст](#контекст-оркестратора) |

## Запуск

В Claude Code (установка плагином): `/orchestrator:limits` объясняет отчёт в нескольких строках, `/orchestrator:costs`
показывает расход, `/orchestrator:status` добавляет прогресс плана. Из оболочки — в клоне репозитория (после настройки
строки состояния скрипты есть и в `~/.claude/claude-orchestrator/`):

```bash
python3 skills/orchestrator/scripts/limits.py            # для человека
python3 skills/orchestrator/scripts/limits.py --json     # для машины
python3 skills/orchestrator/scripts/limits.py --config ~/my-limits.json
python3 skills/orchestrator/scripts/limits.py --session-file <transcript.jsonl> --context-window 1000000
```

| Параметр | Что делает |
|---|---|
| `--json` | Отчёт для машины: `mode`, `data_source`, `session`, `weekly`, `models`, `active_limits`, `context`, `actions`, `calibration`. |
| `--config FILE` | Взять этот конфиг лимитов. |
| `--session-file PATH` | Транскрипт разговора оркестратора (по умолчанию — самый свежий в проекте текущего каталога). |
| `--context-window N` | Окно контекста модели оркестратора в токенах. |
| `--hook [EVENT]` | Режим хука (см. [Хуки](#хуки)): печатать короткое указание, только когда состояние ухудшилось или изменилось. `EVENT` — `PostToolUse`, `UserPromptSubmit` или `SessionStart` (JSON с `additionalContext`); без значения вывод обычным текстом. |
| `--always` | Вместе с `--hook`: выводить, даже если ничего не изменилось. |
| `--cache-sec N` | Вместе с `--hook`: переиспользовать отчёт моложе N секунд (по умолчанию 60). |
| `--now ISO` | Подменить текущее время (для тестов). |

Вывод для человека выглядит так:

```
mode: ECONOMY
session 5h: 28961327 / 45970360 units (63%, cap: statusline), block 2026-05-04T09:50:00+00:00 -> 2026-05-04T14:50:00+00:00
week 7d:    118402220 / 249695560 units (47%)
model fable   ok       week 21304118 / ? (n/a)
model haiku   ok       week 559344 / ? (n/a)
model opus    ok       week 92131516 / ? (n/a)
model sonnet  ok       week 4407242 / ? (n/a)
context: 412880 / 1000000 tokens (41%) -> ok  [3f2a9c1e-….jsonl]
calibration 5h: 1% ≈ 459704 units (learned at 59%, 2026-05-04T12:31Z)
calibration 7d: 1% ≈ 2496956 units (learned at 47%, 2026-05-04T12:31Z)
source: statusline+transcripts
actions:
  - ECONOMY: max 2 parallel heavy agents; no refute panels; prefer haiku for search/build, sonnet for analysis; reviews only for risky changes.
```

Как читать вывод построчно:

- `mode` — уровень ([Уровни](#уровни)).
- `session 5h` — единицы, израсходованные в текущем 5-часовом окне, потолок, процент, откуда взят потолок (`cap:`, см.
  [Окна и потолки](#окна-и-потолки)) и границы окна. При `cap: statusline` процент официальный; пара `units / cap`
  рядом с ним — локальная оценка.
- `week 7d` — то же для скользящей недели.
- `model …` — по семействам моделей: статус (`ok`, `economy`, `off`), недельные единицы и потолок. `?` и `n/a` значат,
  что потолок этого семейства пока неизвестен.
- `context` — токены в разговоре оркестратора, окно, процент и статус.
- `calibration …` — масштаб, полученный по официальным цифрам ([Самокалибровка](#самокалибровка)); печатается, только
  если он есть.
- `source` — `statusline+transcripts` (свежий официальный снимок), `calibrated+transcripts` (свежего снимка нет,
  используется выученный масштаб) или `transcripts` (только оценки).
- Строки `ACTIVE LIMIT …` появляются, пока реальное событие лимита ещё действует.
- `actions` — что оркестратор будет делать в связи с этим.

## Откуда берутся числа (от лучшего к худшему)

1. **Официальные данные строки состояния.** `statusline.py` сохраняет то, что Claude Code передаёт строке состояния, в
   `~/.claude/claude-orchestrator/statusline.json`: `rate_limits.five_hour` / `seven_day` (`used_percentage`,
   `resets_at`) — у подписчиков Pro/Max, и `context_window.used_percentage` — у всех. `limits.py` использует файл,
   только если ему меньше 10 минут. Если данные есть, они заменяют расчётные проценты за 5 часов и 7 дней и время
   конца блока (`cap: statusline`).
2. **Локальные транскрипты.** `~/.claude/projects/*/*.jsonl` и `~/.claude/projects/*/*/subagents/*.jsonl`, файлы,
   изменённые за последние 8 дней; сканируются все проекты, так что учёт идёт по всей машине. `usage` и `model`
   каждого ответа ассистента считаются один раз (дедупликация по id сообщения). Транскрипты субагентов входят в
   подсчёт, так что работа каждой роли учтена.
3. **Реальные события лимитов в транскриптах.** Ошибки вида
   `You've hit your session limit · resets 3:50am (Europe/Berlin)` или `You've hit your Opus limit · …` и
   предупреждения вида `You've used 85% of your session limit`. По ним калибруются потолки.
4. **Самокалибровка.** Пока официальные цифры свежие, `limits.py` узнаёт, сколько единиц составляют 1 % каждого лимита,
   и пользуется этим масштабом, когда снимок устарел (`cap: calibrated`). См. [Самокалибровка](#самокалибровка).
5. **Конфиг** `~/.claude/claude-orchestrator/limits.json` переопределяет потолки, веса, пороги и окно контекста.

Скрипты не видят: расход с других устройств, чаты claude.ai и другой `CLAUDE_CONFIG_DIR`. Каталог данных прежней
версии (v1) по-прежнему читается как запасной источник — см. [Переход с v1](#переход-с-v1).

## Единицы расхода

```
units = вес_модели × ( input + 5·output + 0.1·cache_read + 1.25·cache_write_5m + 2·cache_write_1h )
```

Запись в кэш без разбивки на 5m/1h считается как 5m. Веса по умолчанию (`model_weights`, относительная стоимость
семейства): fable 2.0, opus 1.0, sonnet 0.6, haiku 0.2, other 1.0. Семейство определяется по подстроке в id модели
(`fable`, `opus`, `sonnet`, `haiku`). `costs.py` использует ровно те же единицы.

## Окна и потолки

- **Блоки сессии.** Расход группируется в 5-часовые блоки, начинающиеся с первого запроса после конца предыдущего
  блока. Если в сообщении о лимите указано время сброса, блок привязывается к `[сброс − 5 ч, сброс)`. При наличии
  официальных цифр окно берётся официальное.
- **Неделя.** Скользящие 7 дней (после калибровки — официальное недельное окно).
- **Потолок сессии по реальным событиям.** Для каждого реального события лимита сессии единицы, израсходованные за
  5 часов до него, — одна оценка потолка. Для каждого предупреждения `used N%` (N больше 20) оценка — `units / N`.
  Берётся наибольшая (`cap: observed-limit`).
- **До первого срабатывания.** Потолок — самый большой из завершённых прошлых блоков (`cap: history-max`), это
  предположение с низкой достоверностью. Если завершённых блоков нет, нет ни потолка, ни процента.
- **Недельные и модельные потолки** калибруются так же — по событиям и предупреждениям о недельном лимите,
  `Opus limit` и `Fable limit` за предшествующие 7 дней.
- **Конфиг главнее оценок:** `session_cap_units`, `weekly_cap_units` и `model_weekly_cap_units` имеют приоритет
  (`cap: config`).
- **Разбор времени сброса** понимает формы вроде `resets 3:50am (Europe/Berlin)`, с днём недели или с месяцем и
  числом; неизвестный часовой пояс трактуется как UTC.

Что говорит значение `cap:` в строке `session 5h`:

| `cap:` | Откуда взят 5-часовой процент |
|---|---|
| `statusline` | Официальный процент из свежего снимка строки состояния. |
| `config` | Вы зафиксировали `session_cap_units`. |
| `calibrated` | Масштаб, выученный по прошлым официальным показаниям ([Самокалибровка](#самокалибровка)). |
| `observed-limit` | Потолок, измеренный по реальной ошибке лимита или предупреждению «used N %» в ваших транскриптах. |
| `history-max` | Самый большой из завершённых прошлых блоков — предположение с низкой достоверностью. |

Если подходит несколько вариантов, действует такой порядок: `statusline`, `config`, `calibrated`, `observed-limit`,
`history-max`.

## Самокалибровка

Официальные цифры есть, только пока работает строка состояния, и только у подписчиков Pro/Max. Самокалибровка позволяет
оркестратору сохранять этот масштаб в промежутках — когда снимку больше 10 минут, например во время долгой волны
фоновых агентов или в терминале, где строка состояния не запущена.

**Как это работает.**

1. Каждый раз, когда `limits.py` запускается при свежем снимке строки состояния, он считает единицы расхода внутри
   официального 5-часового окна и делит их на официальный процент. Получается, сколько единиц составляют 1 %
   5-часового лимита. То же самое делается для 7-дневного окна.
2. Масштаб сохраняется в `calibration.json` вместе с процентом, при котором он получен, временем, концом официального
   окна и весами `model_weights`, с которыми считали. Новое показание заменяет старое. Показания ниже 3 % игнорируются,
   а ниже 10 % принимается только первое: целые проценты при малом заполнении слишком грубы.
3. Когда свежего снимка нет, `limits.py` использует сохранённый масштаб вместо потолка, угаданного по прошлым блокам или
   событиям лимита. Потолок становится «единиц на 1 % × 100», а пока сохранённое официальное окно ещё идёт, расход
   считается от начала этого окна, а не от локально угаданного блока. Недельное окно сдвигается шагами по 7 дней от
   сохранённого момента сброса.

**Что значит `cap: calibrated`.** Процент по-прежнему оценка, но привязанная к вашему последнему официальному показанию,
а не к прошлым блокам и событиям лимита. В отчёте при этом `source: calibrated+transcripts` и строки
`calibration 5h: 1% ≈ … units (learned at …)`. Тот же масштаб превращает единицы `costs.py` в «≈ % 5-часового лимита» и
делает возможными бюджеты в процентах ([Бюджеты планов](#бюджеты-планов)).

**Когда он не используется.** Конфиг сильнее: если задан `session_cap_units` или `weekly_cap_units`, потолок остаётся
заданным. Масштаб старше 14 дней игнорируется, как и полученный при других `model_weights`: единицы сопоставимы только
при одинаковых весах. Свежие официальные цифры всегда главнее масштаба.

**Чего он не видит.** И расход, и масштаб берутся из транскриптов этой машины. Расход на других устройствах, в
claude.ai или под другим `CLAUDE_CONFIG_DIR` до них не доходит: между обновлениями такой расход не попадает в оценку, а
если он шёл, пока масштаб обучался, — искажает и сам масштаб. Поэтому значения с `cap: calibrated` — приближение.
Следующее свежее официальное показание заменит оценку и обновит масштаб.

## Уровни

Уровень (`mode`) определяется большим из процентов сессии и недели (официальных, если они есть).

| Уровень | Условие | Поведение оркестратора |
|---|---|---|
| normal | ниже 60 % | до 4 тяжёлых (Opus/Fable) агентов параллельно; полная лестница проверок |
| economy | от 60 % | до 2 тяжёлых агентов; Haiku для поиска и сборок, Sonnet для анализа и документации; ревью только рискованных diff; без панелей опровержения; вопросы агентам пачкой |
| critical | от 80 % | новых тяжёлых агентов нет; завершить начатое; чекпоинт; сообщить, что сделано/осталось и когда сброс; только дешёвые обязательные проверки |
| exhausted | от 95 % или активное событие лимита | ничего не запускать; чекпоинт; после сброса возобновить агентов через `SendMessage` |

Два правила из кода:

- **Активное** событие лимита (сессия, неделя или неизвестный тип; время сброса ещё впереди, а если в тексте его нет —
  5 часов для сессии и 1 час для остальных) всегда даёт `exhausted`.
- Пока потолок только `history-max`, пороги понижаются на одну ступень: от 95 % — `critical` (не `exhausted`),
  от 80 % — `economy`. Диапазон 60–80 % в любом случае `economy`.

## Маршрутизация по моделям

Для каждого семейства (`fable`, `opus` и любого, замеченного за 8 дней) недельный расход сравнивается с его потолком:

| Статус | Условие | Маршрутизация |
|---|---|---|
| `off` | активное событие лимита этой модели; недельная доля не ниже `model_thresholds.off` (0.85); сессия `exhausted` (все семейства); либо только для `fable` — сессия `critical` | см. ниже |
| `economy` | недельная доля не ниже `model_thresholds.economy` (0.60) или сессия `critical` | см. ниже |
| `ok` | иначе | как обычно |

Что делает оркестратор:

| Условие | Действие |
|---|---|
| Fable `off` | все роли Fable/`best` работают на Opus с effort max: `Agent(subagent_type, model: "opus", effort: "max")` или `spawn.sh … --model opus --effort max` |
| Fable `economy` | Fable только как судья критичных и протокольных решений; остальные роли Fable → Opus max |
| Opus `off` | senior-роли → Sonnet с effort high (или Fable, если доступен); ревью последовательно |
| Sonnet `off` | анализ и документация → Haiku high или Opus medium (по справочной политике; `limits.py` пока не печатает для этого случая отдельного указания) |

Fable отключается первым, когда бюджет сессии сжимается, потому что он самый дорогой. Переопределение `effort` в вызове
требует Claude Code 2.1.292 или новее. `model: best` в файлах агентов означает Fable, если он есть у аккаунта, иначе
Opus. Без доступа к Fable строки про Fable на практике не применяются. Через недельную долю модель попадает в `economy`
или `off`, только если для неё известен потолок — из `model_weekly_cap_units` в конфиге либо из записанного события или
предупреждения лимита этой модели; иначе её процент остаётся `n/a`, и сдвинуть статус может только уровень сессии.

## Обработка сбоев (всегда включена)

Если в результате или уведомлении агента встречается `rate_limit`, `429` или `You've hit your … limit`, оркестратор:

1. Классифицирует: привязан к модели (имя модели в тексте) или это лимит сессии/недели.
2. Привязан к модели: переводит это семейство на запасной маршрут (таблица выше) и перезапускает шаг, возобновляя
   упавшего агента через `SendMessage(to: <id>, …)` с переопределением модели/усилия; если возобновить нельзя — новый
   агент с переопределениями.
3. Сессия/неделя: считает это `exhausted` — останавливается, пишет чекпоинт, сообщает вам время сброса. После сброса
   каждого упавшего агента возобновляет фразой «Limit reset — continue from where you stopped and return the result in
   the agreed format.»

В долгих прогонах ворота перезапускаются после завершения каждого агента.

## Контекст оркестратора

Модель не может выполнить `/compact` или `/clear` — только вы. Поэтому оркестратор бережёт контекст (отдаёт всё чтение
агентам, просит отчёты `file:line — факт`, возобновляет агентов вместо повторного брифинга) и реагирует на заполнение:

| Заполнение | Статус | Действие |
|---|---|---|
| ниже 50 % | ok | — |
| от 50 % | `checkpoint` | переписать `## Checkpoint` плана (сделано, id запущенных агентов, следующий шаг, открытые решения, ключевые пути); самому файлы больше не читать |
| от 75 % | `compact` | чекпоинт, затем просьба к вам: `/compact keep: plan <path>, running agent ids, next step` (или начать новую сессию и продолжить по плану) |

Заполнение берётся из снимка строки состояния, если он относится к той же сессии (или если транскрипт не найден), — тогда
используются процент и размер окна, которые сообщает Claude Code. Иначе оно считается по самому свежему транскрипту
проекта текущего каталога (последний ответ ассистента не из sidechain: input + cache read + cache write + output
токены), а окно — это `--context-window`, затем `context_window` из конфига, затем 200k (1M, если когда-либо
наблюдалось больше 200k или в id модели есть `[1m]`).

После `/compact`, `/clear` или resume хук `SessionStart` запускает `checkpoint.py --hook`: он берёт самый свежий
`.claude/plans/*.md` с `Status: in-progress` в шапке и выводит первые 12 строк, раздел `## Checkpoint` (до 80 строк) и
текущую строку о лимитах. Claude Code добавляет этот вывод в новый контекст. Если плана in-progress нет, хук ничего не
печатает. В совсем новую сессию (`startup`) такая подстановка не делается — используйте `/orchestrator:resume`.

Сводка, которую показывает `/orchestrator:status`, строится из `checkpoint.py --status`: прогресс плана, фрагмент
чекпоинта, отчёт о лимитах и расходы.

```
[orchestrator] status — plan .claude/plans/2026-05-04-password-reset.md (in-progress)
progress: 4 done · 2 in progress · 3 to do  ■■■■◧◧□□□ 44%
```

Необязательная настройка (в Claude Code, не в этом плагине): `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`,
`CLAUDE_CODE_AUTO_COMPACT_WINDOW`.

## Расходы

`costs.py` превращает те же транскрипты в отчёт о расходах: сколько токенов и единиц расхода потратили каждая роль и
каждый агент и какая это доля ваших лимитов. В Claude Code его запускает `/orchestrator:costs` и добавляет короткий вывод
с одним советом по экономии.

```bash
python3 skills/orchestrator/scripts/costs.py                       # текущая сессия и её субагенты
python3 skills/orchestrator/scripts/costs.py --project-wide --since 2026-05-04T09:00
python3 skills/orchestrator/scripts/costs.py --plan .claude/plans/2026-05-04-password-reset.md
```

| Параметр | Что делает |
|---|---|
| *(без параметров)* | Текущая сессия: самый свежий транскрипт этого проекта и его субагенты. |
| `--session <id или путь>` | Другая сессия: id (достаточно префикса) или путь к транскрипту. |
| `--project-wide` | Все сессии этого проекта (используйте с `--since`); включает запуски через `spawn.sh`. |
| `--since ISO` | Считать только расход после этого момента (местное время, если смещение не указано). |
| `--plan FILE` | Проверить бюджет плана ([Бюджеты планов](#бюджеты-планов)). Подразумевает подсчёт по всему проекту с начала плана. |
| `--active-plan` | Взять самый свежий план в работе как `--plan`. |
| `--budget-only` | Печатать только строку бюджета; без бюджета молчит. |
| `--top N` | Сколько главных агентов показывать (по умолчанию 8). |
| `--json` | Отчёт для машины. |
| `--hook [EVENT]` | Режим хука: молчит, пока активный план не перешёл 80 % / 100 % бюджета. |
| `--config FILE` | Конфиг лимитов, из которого брать веса моделей. |

**Что такое единицы.** Токены, взвешенные по их стоимости, чтобы можно было складывать разные модели и виды токенов:
выходные токены считаются с коэффициентом 5, чтение кэша — 0.1, запись в кэш — 1.25 (5 минут) или 2 (1 час), а у каждого
семейства моделей свой вес (Fable 2.0, Opus 1.0, Sonnet 0.6, Haiku 0.2). Формула — в разделе
[Единицы расхода](#единицы-расхода).

Отчёт:

```
Costs — session 3f2a9c1e · since 2026-05-04 09:52Z · 412 responses
  total: 61.2M tokens · 8.47M units · ≈ 18.4% of the 5-hour limit · ≈ 3.4% of the week

  role                         agents   model   tokens    units   ≈5h %  share
  orchestrator (main)               1    opus    24.1M    3.52M    7.7%    42%
  orch-dev-senior                   2    opus    19.8M    2.61M    5.7%    31%
  orch-reviewer                     2    opus    9.40M    1.37M    3.0%    16%
  orch-tech-writer                  1  sonnet    3.10M   402.5k    0.9%     5%
  orch-security                     1   fable    1.20M    388.0k    0.8%     5%
  orch-scout                        3   haiku    3.60M   121.0k    0.3%     1%
  orch-build-verifier               2   haiku   0.20M    14.2k     0.0%     0%

  top agents:
    orch-dev-senior        a3de429a5d    1.52M units  opus   API + web client for password reset
    orch-reviewer          a0bfb4ae2d    0.81M units  opus   Review backend changes

  budget (2026-05-04-password-reset.md): 25% of the 5-hour limit → spent 18.4% = 74% → OK
```

| Колонка | Что значит |
|---|---|
| `role` | Тип субагента (`orch-reviewer`), `orchestrator (main)` — сам разговор, или `subagents (inline)` — ответы sidechain, записанные в главном транскрипте. |
| `agents` | Сколько отдельных агентов этой роли работало. |
| `model` | Семейство модели, потратившее больше всего единиц этой роли. |
| `tokens` | Все токены: input, output, чтение и запись кэша. Чтений кэша много, но они дешёвые, поэтому токенов в несколько раз больше, чем единиц. |
| `units` | Те же токены, взвешенные по цене, — [единицы расхода](#единицы-расхода) выше. |
| `≈5h %` | Единицы, делённые на число единиц в 1 % 5-часового лимита. Нужна калибровка ([Самокалибровка](#самокалибровка)); недельная цифра в шапке считается так же. |
| `share` | Доля роли во всех единицах. |

**Как определяются роли.** Claude Code хранит транскрипт каждого субагента рядом с сессией
(`<session>/subagents/agent-<id>.jsonl`), а рядом с ним — `agent-<id>.meta.json`. `costs.py` берёт из этого meta-файла
`agentType` (`orchestrator:orch-reviewer` показывается как `orch-reviewer`) и `description`, с которым агента запустили, —
оно выводится в блоке «top agents». Субагент без meta-файла попадает в список как `subagent`. Ответы дедуплицируются по
id сообщения, поэтому ничего не считается дважды; агенты, ничего не потратившие, в список не попадают.

**Без калибровки** колонки `≈ %` показывают `n/a`, а отчёт добавляет примечание: они появятся, когда строка состояния
хотя бы раз сообщит официальные цифры.

## Бюджеты планов

План может ограничивать собственный расход. Поставьте в шапке плана строки `Budget:` и `Started:` (читаются только
первые 4000 символов файла); в шаблоне [`templates/plan.md`](../../skills/orchestrator/templates/plan.md) обе уже есть:

```
**Date:** 2026-05-04 · **Status:** in-progress
**Started:** 2026-05-04 09:52 · **Budget:** 25%
```

| Запись в шапке | Что значит | Нужна ли калибровка |
|---|---|---|
| `Budget: 25%` | 25 % 5-часового лимита | да |
| `Budget: 4M tokens` | 4 миллиона токенов (суффиксы `k` и `M` понимаются; число без слова считается токенами) | нет |
| `Budget: 2.5M units` | 2,5 миллиона [единиц расхода](#единицы-расхода) | нет |

Токены здесь включают чтение кэша, поэтому бюджет в токенах выбирается быстрее, чем лимит; бюджет в `%` или в `units`
точнее следует реальному расходу лимита.

**Что считается.** Все сессии проекта с момента `Started:` — `YYYY-MM-DD HH:MM` по местному времени. Если этой строки
нет, берётся строка `Date:`, а если нет и её — время создания файла плана. Транскрипты субагентов и запуски через
`spawn.sh` входят в подсчёт.

**Что делает хук.** После каждого вызова инструмента `Agent` хук бюджета (`costs.py --hook PostToolUse`) смотрит на самый
свежий план в работе со строкой `Budget:` и обращается к оркестратору один раз при пересечении каждой отметки:

- При 80 % бюджета:
  `[orchestrator budget] plan .claude/plans/2026-05-04-password-reset.md: 82% of the budget (25% of the 5-hour limit) spent. Prefer cheaper models, avoid optional reviews and scope growth; tell the user if the rest will not fit.`
- При 100 %: бюджет объявляется исчерпанным, с указанием не запускать новых агентов, довести начатое до конца или
  зафиксировать его чекпоинтом и спросить вас, продлевать ли бюджет.

Хук молчит, если нет плана в работе, нет строки `Budget:` или бюджет в `%` задан, а калибровки ещё нет (уровень читается
как `UNKNOWN` — один раз включите строку состояния). Чтобы продлить бюджет, поправьте строку в плане.

**Проверка вручную.** `costs.py --plan <plan.md>` печатает отчёт по этому плану; `costs.py --active-plan --budget-only` —
только строку бюджета самого свежего плана в работе.

## Хуки

`hooks/hooks.json` регистрирует четыре хука (три события Claude Code; у `SessionStart` два matcher). Хуки кладут указания
в контекст оркестратора и никогда не блокируют вызов инструмента. Если всё в порядке, они молчат.

| Событие | Команда | Что делает |
|---|---|---|
| `SessionStart` (`startup`) | `scripts/sync_stable.py` | Обновляет стабильную копию скриптов после обновления плагина (см. ниже). |
| `SessionStart` (`compact\|resume\|clear`) | `checkpoint.py --hook` | Возвращает чекпоинт плана и строку о лимитах. |
| `PostToolUse` (`Agent`) | `limits.py --hook PostToolUse`<br>`costs.py --hook PostToolUse` | После каждого запуска или завершения агента: указание по лимитам, если состояние ухудшилось или изменилось; предупреждение о бюджете при 80 % / 100 %. |
| `UserPromptSubmit` | `limits.py --hook UserPromptSubmit --cache-sec 120` | То же указание по лимитам, один раз на запрос. |

**Хук лимитов.** Последнее состояние (режим, статусы моделей, статус контекста) он хранит в
`~/.claude/claude-orchestrator/last-state.json` и говорит, только когда оно изменилось, — в том числе когда состояние
восстановилось. Если всё в порядке, первый вызов тоже молчит. Отчёты кэшируются в `last-report.json` на `--cache-sec`
секунд (по умолчанию 60, для `UserPromptSubmit` — 120), чтобы не перечитывать транскрипты при каждом вызове. Путь к
транскрипту текущего разговора хук берёт из своих входных данных. Любое исключение уходит в stderr, а хук завершается с
кодом 0, поэтому сессию он сломать не может. Сообщение выглядит так:

```
[orchestrator limits] mode=economy session=63% week=47% context=41% models=fable:ok,haiku:ok,opus:ok,sonnet:ok :: ECONOMY: max 2 parallel heavy agents; no refute panels; prefer haiku for search/build, sonnet for analysis; reviews only for risky changes.
```

`--always` включает вывод даже без изменений. Хук бюджета хранит своё состояние в `costs-state.json`.

**Синхронизация стабильной копии при старте.** Команда строки состояния и хуки ручной установки не должны указывать
внутрь каталога самого плагина: он меняется с каждой версией. Поэтому они запускают стабильную копию в
`~/.claude/claude-orchestrator/`. В начале каждой сессии `sync_stable.py` сравнивает эту копию (`limits.py`,
`statusline.py`, `checkpoint.py`, `costs.py`) со скриптами плагина и обновляет то, что отличается, — но только если вы
настроили строку состояния (там есть `statusline.py`). Скрипт молчит и игнорирует ошибки.

**Ручная установка.** Добавьте `--hooks` к `install.sh`: он зарегистрирует в `settings.json` хуки чекпоинта, лимитов и
бюджета, указывающие на `~/.claude/claude-orchestrator/`. Синхронизация при старте есть только у плагина; после
`git pull` снова запустите `./install.sh`, чтобы обновить копию. Не сочетайте плагин с `--hooks`, иначе каждый хук
сработает дважды.

## Строка состояния

`statusline.py` печатает одну строку и сохраняет описанный выше снимок:

```
Opus 5.5 · ctx 41% · 5h 63% ↻14:50 · 7d 22%
```

Части `5h` и `7d` появляются, только если Claude Code передаёт `rate_limits` (Pro/Max); `ctx` — когда доступен процент
контекста; `↻` — локальное время сброса.

**Настройка, один раз.** Плагин не может поставлять строку состояния, поэтому включите её сами:

```
/orchestrator:setup                  # установка плагином, набирается в Claude Code
./install.sh --statusline            # ручная установка
```

`/orchestrator:setup` запускает `install.sh --statusline-only`. Команда копирует скрипты в
`~/.claude/claude-orchestrator/`, добавляет запись `statusLine` в `~/.claude/settings.json` и перед этим делает
резервную копию `settings.json.bak-<время>`. Строка появится после вашего следующего сообщения (если нет — перезапустите
Claude Code); `5h` и `7d` на Pro/Max показываются после первого ответа. После обновления плагина копия скриптов
обновляется сама при следующем запуске сессии.

**Уже имеющаяся строка состояния сохраняется.** Её команда запоминается в `ORCH_STATUSLINE_NEXT` внутри новой команды, а
её вывод дописывается после ` | ` (таймаут 5 секунд). Повторная настройка безопасна: цепочка сохраняется. Чтобы
прописать всё вручную, добавьте в `settings.json` с абсолютным путём:

```json
"statusLine": { "type": "command", "command": "python3 /ABS/PATH/statusline.py" }
```

**Отмена.** Перед удалением плагина наберите `/orchestrator:setup remove`. Команда убирает только запись строки
состояния и хуков Orchestrator и возвращает вашу прежнюю строку (копия `settings.json` остаётся); папка данных
`~/.claude/claude-orchestrator` (калибровка, ваш `limits.json`, если он есть) не трогается. При ручной установке
`./uninstall.sh` убирает записи, папку данных, скилл и агентов.

## Конфигурация

Файл: `~/.claude/claude-orchestrator/limits.json`, либо путь из `$ORCH_LIMITS_CONFIG`, либо `--config <file>`. Берётся
первый существующий, в порядке `--config`, `$ORCH_LIMITS_CONFIG`, файл по умолчанию; его ключи накладываются на значения
по умолчанию (вложенные объекты сливаются по ключам). Шаблон:
[`examples/limits.example.json`](../../examples/limits.example.json).

```json
{
  "session_cap_units": null,
  "weekly_cap_units": null,
  "model_weekly_cap_units": { "fable": null, "opus": null },
  "model_weights": { "fable": 2.0, "opus": 1.0, "sonnet": 0.6, "haiku": 0.2, "other": 1.0 },
  "thresholds": { "economy": 0.60, "critical": 0.80, "exhausted": 0.95 },
  "model_thresholds": { "economy": 0.60, "off": 0.85 },
  "context_window": null,
  "context_thresholds": { "checkpoint": 0.50, "compact": 0.75 }
}
```

Примеры:

```json
{ "session_cap_units": 40000000 }
```
Фиксирует потолок 5 часов. Подходит, когда вы увидели реальное число в выводе `limits.py` после записанного сообщения
о лимите, либо когда оценка постоянно промахивается. Заодно не даёт самокалибровке подменить потолок.

```json
{ "thresholds": { "economy": 0.50, "critical": 0.70, "exhausted": 0.90 } }
```
Более осторожный оркестратор.

```json
{ "context_window": 200000, "context_thresholds": { "checkpoint": 0.40, "compact": 0.65 } }
```
Принудительно окно 200k и более ранние чекпоинты.

```json
{ "model_weekly_cap_units": { "fable": 6000000 } }
```
Задаёт Fable недельный потолок, чтобы его доля могла дойти до `economy`/`off` ещё до реальной ошибки лимита Fable.

Смена `model_weights` заодно сбрасывает сохранённую калибровку: она выучивается заново.

## Каталог данных и переменные окружения

Всё, что пишут скрипты, лежит в `~/.claude/claude-orchestrator/` (внутри `CLAUDE_CONFIG_DIR`, если он задан):

| Файл | Что это |
|---|---|
| `statusline.json` | Последний официальный снимок, записанный строкой состояния; читается, только если ему меньше 10 минут. |
| `calibration.json` | Выученное число единиц в 1 % 5-часового и недельного лимитов. |
| `limits.json` | Ваша необязательная конфигурация. |
| `last-state.json`, `last-report.json` | Состояние и кэш хука лимитов. |
| `costs-state.json` | Последний уровень бюджета, о котором сообщили, по каждому плану. |
| `limits.py`, `statusline.py`, `checkpoint.py`, `costs.py` | Стабильная копия скриптов (после настройки строки состояния или ручной установки). |

Переменные окружения: `CLAUDE_CONFIG_DIR` (где Claude Code хранит свои данные; по умолчанию `~/.claude`),
`ORCH_LIMITS_CONFIG` (путь к конфигу лимитов), `ORCH_STATUSLINE_NEXT` (команда другой строки состояния, вывод которой
дописывается к нашему), `CLAUDE_PROJECT_DIR` (Claude Code задаёт её для хуков; `costs.py` и `checkpoint.py` по ней находят проект).

## Если что-то не так

**Режим `economy` (или `critical`), а лимит я не исчерпал.** До первого записанного события лимита потолок — самый
большой завершённый прошлый блок (`cap: history-max`). Если текущий блок больше всех предыдущих, процент по построению
выше 100 %, а при короткой истории потолок занижен. Запустите `limits.py` и посмотрите `cap:`. Что делать: включить
строку состояния (Pro/Max), чтобы использовались официальные проценты и выученный масштаб; задать `session_cap_units`;
либо поднять `thresholds`.

**`cap: history-max` и проценты `n/a`.** За последние 8 дней ещё нет завершённого блока, сравнивать не с чем. Режим
остаётся `normal`, пока не накопятся данные (проверки контекста при этом работают).

**`/orchestrator:limits` пишет, что источник — только `transcripts`.** Официальные данные до скрипта не дошли. На Pro/Max
включите строку состояния (`/orchestrator:setup`), чтобы получать точные цифры; с API-ключом остаются оценки.

**Строка состояния пустая.** Проверьте настройки: `statusLine` должна указывать на существующий `statusline.py`
(`python3` должен быть в `PATH`). Claude Code запускает команду строки состояния только после того, как рабочая папка
помечена доверенной, — сначала примите диалог доверия для папки. Выполните
`echo '{}' | python3 ~/.claude/claude-orchestrator/statusline.py` — должна напечататься строка. Требование доверия
исходит от Claude Code, а не от этого пакета; подробности — в документации Claude Code.

**В строке состояния нет `5h` / `7d`.** `rate_limits` передаётся только подписчикам Pro/Max и только после первого
ответа в сессии. Иначе используются оценки по транскриптам.

**После обновления плагина строка состояния работает на старом коде.** Копия в `~/.claude/claude-orchestrator/`
обновляется при следующем запуске сессии; чтобы обновить её сразу, снова выполните `/orchestrator:setup`.

**Контекст показывает `unknown`.** Для текущего каталога не найден транскрипт, а снимок строки состояния старше
10 минут или относится к другой сессии. Включите строку состояния или передайте `--session-file`.

**Проценты расходятся с `/usage`.** Это ожидаемо: оценки учитывают только транскрипты этой машины и фиксированную
структуру цен ([Чего он не видит](#самокалибровка)). Доверяйте официальным числам; если хотите, чтобы оценки были ближе,
задайте потолки в конфиге.

**`costs.py` показывает `n/a` в колонках `≈ %` или бюджет читается как `UNKNOWN`.** Калибровки ещё нет. Включите строку
состояния на тарифе Pro/Max и дайте `limits.py` отработать хотя бы раз при свежем снимке (это делает любой хук); бюджеты
в `tokens` и `units` работают и без неё.

**Хук лимитов никогда ничего не говорит.** Так задумано: пока всё `normal`/`ok` и ничего не менялось, он молчит. Посмотрите
`~/.claude/claude-orchestrator/last-state.json` или запустите `limits.py --hook --always`.

**Хук бюджета молчит.** Ему нужен план в работе со строкой `Budget:` в первых 4000 символах, и он говорит только при
пересечении отметок 80 % и 100 % (по одному разу). Проверьте командой `costs.py --active-plan --budget-only`.

**Хуки срабатывают дважды.** Вы поставили плагин и дополнительно запустили `install.sh --hooks`. Удалите из
`~/.claude/settings.json` записи `hooks`, где упоминается `claude-orchestrator`, или запустите `./uninstall.sh` (он
удаляет всю ручную установку, включая строку состояния, — после этого снова выполните `/orchestrator:setup`).

**Версия Python.** Нужен 3.9+ (`zoneinfo`); на более старых версиях часовые пояса в текстах сброса заменяются на UTC.

## Переход с v1

До 2.0.0 продукт назывался Team Orchestrator (плагин `team-orchestrator`). Что меняется для лимитов и данных:

- **Каталог данных.** Всё теперь лежит в `~/.claude/claude-orchestrator/` вместо `~/.claude/team-orchestrator/`. Старый
  каталог по-прежнему читается как запасной источник — для `limits.json` и для снимка строки состояния (побеждает более
  свежий из двух, так что старая строка состояния v1 продолжает кормить новые скрипты, пока вы не переключитесь). Новые
  скрипты пишут только в новый каталог. Калибровка начинается с нуля и выучивается заново, как только строка состояния
  снова сообщит официальные цифры.
- **Хуки.** Хуки плагина исчезают вместе с плагином v1. Записи, которые ручная установка v1 внесла в `settings.json`,
  заменяются при запуске `./install.sh --hooks` новой версии и удаляются её `./uninstall.sh`.
- **Строка состояния.** Один раз выполните `/orchestrator:setup` (плагин) или `./install.sh --statusline` (ручная
  установка): `settings.json` переключится на новый каталог, а ваша собственная строка состояния, которая выводилась
  после старой, сохранится. Перед этим делается резервная копия.
- **Уборка.** Когда новая строка состояния заработает, скопируйте нужный `limits.json` в новый каталог, а старый
  удалите:

```bash
mkdir -p ~/.claude/claude-orchestrator
cp ~/.claude/team-orchestrator/limits.json ~/.claude/claude-orchestrator/   # только если он у вас был
rm -rf ~/.claude/team-orchestrator
```

Переименования (плагин, маркетплейс, команды, агенты) и шаги перехода для плагина собраны в
[руководстве по использованию](usage-guide.md#переход-с-v1).
