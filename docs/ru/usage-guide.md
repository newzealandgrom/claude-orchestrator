# Руководство по использованию

[English version](../en/usage-guide.md) · [README](../../README.ru.md) · [Лимиты и контекст](limits-and-context.md)

Здесь по шагам разобрана одна оркестрируемая задача — от запроса до отчёта, а затем: как продолжить работу, как писать
брифы, как работать параллельно и как не тратить лишнего. Всё описанное взято из самого скилла
(`skills/team-orchestrator/SKILL.md` и `references/`).

## Запуск

```
/team-orchestrator <задача>            # новая задача
/team-orchestrator resume              # продолжить план из .claude/plans/ со статусом in-progress
/team-orchestrator .claude/plans/2026-10-13-api-tests.md   # продолжить конкретный план
```

Скилл также подключается автоматически, если запрос подходит под его описание (изменения в нескольких файлах или
платформах, аудиты и исправление находок, релизы, деплой, ревью). При установке плагином полная форма —
`/team-orchestrator:team-orchestrator`. Оркестратор отвечает на вашем языке.

## Жизненный цикл

### 0. Ворота лимитов

Первый шаг и повтор перед каждой волной агентов: `python3 scripts/limits.py`. Скрипт печатает `mode`, статус по
моделям, заполнение контекста и список действий, которым затем следует оркестратор. См.
[limits-and-context.md](limits-and-context.md).

### 1. Размер задачи

| Размер | Признаки | Что происходит |
|---|---|---|
| S | не больше 2 файлов, очевидная правка, без безопасности/прода/протокола | Оркестратор делает сам, без агентов. |
| M | 2–6 шагов, 1–2 области | Короткий план, 2–5 агентов, проверка. |
| L | несколько платформ или сервисов, протокол/крипто/безопасность, прод, пачка находок аудита, новая функция | Полный цикл; сначала план смотрит архитектор. |

### 2. Разведка (дёшево)

- Читается карта проекта `.claude/orchestrator/project-map.md`; если её нет, `orch-scout` (Haiku) строит её по
  `references/project-map-template.md` (структура, команды сборки и тестов, факты о проде, ловушки).
- Проверяются память и `.claude/plans/`.
- Scout возвращает карты `file:line — что`, по одной на область, параллельно. `orch-devops` может снять снимок прода в
  режиме «только чтение». Код оркестратор открывает сам лишь для приёмки результатов.

### 3. План

Файл `.claude/plans/YYYY-MM-DD-<slug>.md` по `templates/plan.md`: шаги с `file:lines`, роль и модель/усилие,
зависимости, что идёт параллельно, «готово, когда» и команда проверки на каждый шаг, гейт на прод, оценка токенов и
раздел `## Checkpoint`. Для задач L план смотрит `orch-architect`, каждое расхождение разбирается явно. Вам
показывают сводку на 5–12 строк; дальше оркестратор идёт сам, если следующий шаг не необратим и не затрагивает прод.

### 4. Исполнение

- Каждый агент получает бриф по `templates/brief.md` — это единственный его контекст.
- Один писатель на файл; параллельные писатели в одном дереве сборки работают в отдельных git worktree.
- Фоновые агенты сообщают о завершении сами; оркестратор не угадывает их результат.
- Эскалация: сначала самая дешёвая подходящая модель; при неудаче — следующий уровень с тем же брифом и причиной
  неудачи.

### 5. Проверка

Пропорциональна риску, на слово разработчику не верят: `orch-build-verifier` — всегда; `orch-reviewer` — на каждый
шаг разработки; `orch-protocol-reviewer` — для крипто, auth, wire-форматов; `orch-security` — для auth, периметра,
rate limits и конфигурации прода; `orch-qa` — для пользовательских сценариев. Вердикт «на доработку» возвращается тому
же разработчику через `SendMessage` (контекст сохраняется), затем перепроверяются только исправления. Для критичных
находок — панель из трёх независимых ревьюеров (принимается при двух и более). См. `references/verification.md`.

### 6. Гейт на прод

Деплой, перезапуск, правка конфигов и файрвола, `git push`, публикация, удаление, ротация секретов — ничего из этого не
происходит без вашего явного «да» на конкретный шаг в текущем разговоре, если сам запрос прямо не требует именно этого
действия. Порядок: снимок только для чтения -> план с бэкапом и откатом -> ваше «да» -> бриф для `orch-devops` с
`OWNER_APPROVED: yes` и точным списком действий -> проверки после изменения. См. `references/production-gate.md`.

### 7. Завершение

План получает статус `done` и раздел «Result» (сделано / не сделано и почему / чем проверено / что должен сделать
владелец / токены). Устойчивые факты уходят в карту проекта. Итоговый отчёт: что изменено, как проверено (команды ->
результаты), что осталось и какое решение нужно от вас.

## Пример сессии (сокращённо, иллюстрация)

```
вы       > /team-orchestrator fix the failing tests in api/ and add coverage

orch     > [limits] mode normal, fable ok, context 6%.
           Размер: M (только api/, 2 области: обработчики + тесты). Сначала разведка.
orch     > scout (haiku): карта api/, команды тестов -> .claude/orchestrator/project-map.md обновлён
orch     > План .claude/plans/2026-10-13-api-tests.md
           1. orch-build-verifier: `pytest api/ -x -q`, список падений            (haiku/low)
           2. orch-dev-middle: починить обработчики в api/orders.py:40-120        (sonnet/medium)
           3. orch-dev-middle: покрытие для api/orders.py (отдельный файл)         (sonnet/medium)   параллельно с 2
           4. orch-build-verifier + orch-reviewer на оба diff                      (haiku/low, opus/high)
           Прод не затрагивается. Оценка ~0.4M токенов. Продолжаю.
orch     > шаг 1: 3 падения, все в api/orders.py (строки 58, 77, 112)
orch     > шаги 2 и 3 идут параллельно (разные файлы; pytest запускается по очереди)
orch     > шаг 2 готов; шаг 3 готов
orch     > build-verifier: PASS (41 passed). reviewer: на доработку — нет негативного случая для пустой корзины
orch     > SendMessage разработчику шага 3: добавить случай; reviewer перепроверяет только исправление
orch     > принято.

Отчёт
  Изменено: api/orders.py:58-64,77-81,112-118 (исправления); tests/test_orders.py (+9 тестов)
  Проверено: pytest api/ -q -> 50 passed; reviewer, раунд 2: принято
  Не проверено: поведение под нагрузкой
  Осталось / нужны решения: нет
```

Числа и имена файлов здесь выдуманы, чтобы показать форму сессии; это не реальный вывод.

## Как продолжить работу

**После `/compact`, `/clear` или `--resume`.** Хук `SessionStart` плагина (matcher `compact|resume|clear`) находит
самый свежий план в `.claude/plans/*.md`, в шапке которого указано `in-progress`, и кладёт в новый контекст его
шапку, раздел `## Checkpoint` и однострочную сводку о лимитах. Если оркестратор сам не продолжил работу, выполните
`/team-orchestrator resume`.

**После лимита.** В режиме `exhausted` оркестратор ничего не запускает, пишет чекпоинт и сообщает время сброса.
После сброса скажите `resume`: упавших или завершённых агентов продолжают через `SendMessage`
(«Limit reset — continue from where you stopped and return the result in the agreed format.»), а не брифуют заново.

**Просьба о `/compact`.** Модель не может выполнить `/compact`. При 75 % контекста она записывает чекпоинт и просит вас
выполнить команду с подсказкой вида `/compact keep: plan <path>, running agents, next step`.

В хорошем чекпоинте (раздел шаблона) перечислено: что сделано, что в работе (id агента и что он делает), следующий шаг,
открытые решения и вопросы к вам, ключевые пути. Если правите план вручную, оставьте строку
`**Status:** in-progress` в первых 4000 символах — хук ищет её там (`checkpoint.py` понимает и русские слова
«статус» и «чекпоинт»).

## Как писать хорошие брифы

Если вы брифуете агентов сами (или проверяете бриф оркестратора), берите `templates/brief.md`:

```
ROLE: orch-<role> · PLAN: .claude/plans/<file>.md, step <N>
GOAL: <одно предложение — что должно быть истинно после вашей работы>

CONTEXT (ready-made, do not search again):
- <file>:<A>-<B> — <что там> → read with `sed -n A,Bp <file>`

DO:
1. …

CONSTRAINTS:
- You may edit only: <files/dirs>. Everything else: report, do not touch.

DONE WHEN:
- <проверяемое утверждение>
- <негативный сценарий, который должен безопасно провалиться>

VERIFY (run yourself, attach output):
- `<команда>`

PRODUCTION: do not touch.
REPORT FORMAT: changes as `file:lines — what`, command outputs, deviations with reasons, what is not done.
```

Практические правила: давайте диапазоны (`file:A-B`), а не целые файлы; перечисляйте файлы, которые агент вправе
менять; формулируйте негативный сценарий; просите структурированный отчёт, а не прозу; разрешение на прод указывайте
явно (`PRODUCTION: do not touch` или `OWNER_APPROVED: yes — allowed exactly: …; rollback: …`). Шаблон брифа на
английском, и агенты читают его в таком виде; отвечать вам оркестратор будет на вашем языке.

## Параллельная работа

- Один писатель на файл. Большой контроллер или серверный файл правит один агент за раз.
- Разные файлы в одном скомпилированном дереве (один проект gradle/xcode/npm) всё равно могут ломать друг другу сборку.
  Второго писателя запускают с `isolation: "worktree"`; он коммитит в своей ветке и сообщает хеш. Оркестратор
  переносит изменения без коммита:

```bash
git cherry-pick -n <sha>
```

  Это работает на «грязном» дереве, если затронутые файлы там не изменены. Последующие правки — новые коммиты, они
  переносятся так же. Добавьте `.claude/worktrees/` в `.gitignore` репозитория.
- Не больше одной тяжёлой сборки каждого инструмента на дерево; для параллельных сборок Xcode — отдельные каталоги
  derived data.
- Лимиты параллелизма: `normal` — до 4 тяжёлых агентов, `economy` — до 2, `critical` — новых нет.
- Проверяйте, что новые исходники не попали в игнор молча (`git status --short --ignored <dir>`).

## Карта проекта

`.claude/orchestrator/project-map.md` (около 150 строк максимум) читается часто, поэтому короткая: что за проект,
компоненты и размеры, команды сборки/тестов/линтеров, полезные спецификации, факты о проде (только чтение), ловушки.
Первый раз её строит scout; оркестратор обновляет, когда она устаревает. Шаблон — `references/project-map-template.md`.
Коммитить её или игнорировать — на ваше усмотрение. Секреты в неё класть нельзя: её читают часто и она может попасть в
коммит.

## Как не тратить лишнего

- Маленькие задачи оставляйте маленькими: S делается напрямую.
- Передавайте в брифах карты и диапазоны, чтобы дорогие агенты не искали сами.
- Лучше возобновить агента (`SendMessage`), чем брифовать нового.
- Сначала самая дешёвая подходящая модель; Fable/`best` — только для архитектуры, безопасности, протоколов и
  критичных решений.
- Просите компактные отчёты; не вставляйте большие файлы и полные diff в чат оркестратора.
- Поставьте строку состояния и следите за `ctx` — чекпоинт лучше сделать заранее, чем сжимать контекст в спешке.
- Режим `economy` — сигнал, а не помеха: он нужен, чтобы успеть закончить задачу до сброса окна.
- Ориентировочная стоимость агента (из `references/model-routing.md`): scout 5–50k токенов, build-verifier 5–30k,
  junior 10–30k, middle 30–100k, senior 60–500k, reviewer 40–300k, architect/protocol/security 60–300k. План из пяти
  шагов разработки с полной проверкой: 0.5–1.5M; кросс-платформенное изменение протокола с раундами ревью: 3–7M.
