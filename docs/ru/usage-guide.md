# Руководство по использованию

[English version](../en/usage-guide.md) · [README](../../README.md#russian) · [Лимиты и контекст](limits-and-context.md)

Claude Orchestrator превращает нетривиальный запрос в план, раздаёт шаги ролевым субагентам на подходящей модели и с
подходящим усилием, проверяет результат и отчитывается — а заодно следит за вашими лимитами, расходом токенов и за
собственным окном контекста. В руководстве: установка, команды, путь одной задачи от запроса до отчёта, состав из
27 ролей и плейбуки, как продолжить работу, как писать брифы, параллельная работа и готовые рецепты. Всё описанное
взято из самого скилла ([`skills/orchestrator/SKILL.md`](../../skills/orchestrator/SKILL.md) и
[`references/`](../../skills/orchestrator/references/)). О том, как устроены лимиты, расходы и контекст, подробно
рассказано в разделе [Лимиты и контекст](limits-and-context.md).

## Установка

Что понадобится: Claude Code (лучше 2.1.292 или новее — для запасных маршрутов по моделям используется `effort` на
уровне агента; для однострочной установки ниже нужна версия 2.1.275 или новее), Python 3.9+ только со стандартной
библиотекой (ничего ставить через `pip` не нужно) и macOS или Linux (в Windows — через WSL: скрипты написаны на bash и
Python). С подпиской Claude Pro/Max строка состояния показывает точные официальные цифры лимитов, с API-ключом — только
оценки.

### Внутри Claude Code (рекомендуется)

1. Откройте терминал (macOS — Terminal или iTerm, Linux — любой, Windows — WSL Ubuntu), перейдите в папку проекта и
   запустите Claude Code:

   ```bash
   cd ~/my-project
   claude
   ```

2. В поле ввода Claude Code (строка с `>`) наберите одну строку:

   ```
   /plugin install orchestrator --marketplace newzealandgrom/claude-orchestrator
   ```

   Claude Code версии ниже 2.1.275 однострочную форму не знает. Тогда — две команды:

   ```
   /plugin marketplace add newzealandgrom/claude-orchestrator
   /plugin install orchestrator@claude-orchestrator
   ```

3. Если новые команды не появились сразу, наберите `/reload-plugins` или перезапустите Claude Code.

### Из терминала

Не открывая Claude Code:

```bash
claude plugin install orchestrator --marketplace newzealandgrom/claude-orchestrator
```

Чтобы включить плагин только для текущего проекта, добавьте `--scope project` (по умолчанию область — пользовательская).
На старой версии Claude Code — в два шага: `claude plugin marketplace add newzealandgrom/claude-orchestrator`, затем
`claude plugin install orchestrator@claude-orchestrator`.

### Ручная установка (копирование файлов, без системы плагинов)

```bash
git clone https://github.com/newzealandgrom/claude-orchestrator.git
cd claude-orchestrator
./install.sh
```

| Параметр | Что делает |
|---|---|
| *(без параметров)* | Ставит скилл и 27 агентов `orch-*` для вашего пользователя (`~/.claude`). Скрипты дополнительно копируются в `~/.claude/claude-orchestrator/`. |
| `--project <dir>` | Скилл и агенты только для одного проекта (`<dir>/.claude`). |
| `--statusline` | Дополнительно включает строку состояния (правит `settings.json`). |
| `--hooks` | Дополнительно регистрирует в `settings.json` хуки лимитов, бюджета и чекпоинта. В плагине они уже встроены — не включайте оба варианта сразу. |
| `--statusline-only` | Только строка состояния, без скилла и агентов. Именно это запускает `/orchestrator:setup` у пользователей плагина. |
| `--dry-run` | Показать, что изменится, ничего не меняя. |

Перед любыми правками `settings.json` копируется в `settings.json.bak-<timestamp>`; переменная `CLAUDE_CONFIG_DIR`
учитывается. Ручная установка даёт команду `/orchestrator` (без префикса) и агентов с именами `orch-<role>`.

### Как проверить, что всё встало

- `/plugin` → на вкладке «Installed» виден `orchestrator`.
- `/agents` показывает 27 агентов `orchestrator:orch-…`.
- Наберите `/orchestrator:` — в меню появятся команды.
- `/orchestrator:limits` печатает отчёт о лимитах.

### Строка состояния (по желанию, рекомендуется, один раз)

Плагин не может сам включить строку состояния, поэтому это отдельный шаг. Пользователям плагина достаточно набрать:

```
/orchestrator:setup
```

Команда запускает `install.sh --statusline-only`: копирует скрипты в `~/.claude/claude-orchestrator/`, добавляет запись
`statusLine` в `~/.claude/settings.json`, делает резервную копию `settings.json.bak-<время>` и сохраняет уже имеющуюся у
вас строку состояния (её вывод показывается после нашего). При ручной установке — `./install.sh --statusline`. Строка
появится после вашего следующего сообщения:

```
Opus 5.5 · ctx 41% · 5h 63% ↻14:50 · 7d 22%
```

На Pro/Max она к тому же отдаёт точные цифры проверкам лимитов оркестратора. После обновления плагина копия скриптов
обновляется сама при следующем запуске сессии. Подробности и отмена — в разделе
[Строка состояния](limits-and-context.md#строка-состояния).

## Запуск

```
/orchestrator:orchestrator <задача>          # новая задача (установка плагином)
/orchestrator <задача>                       # то же при ручной установке
/orchestrator:orchestrator resume            # продолжить план из .claude/plans/ со статусом in-progress
/orchestrator:orchestrator .claude/plans/2026-05-04-password-reset.md   # продолжить конкретный план
```

Можно и просто попросить словами: «Используй оркестратор, чтобы …». Claude сам подключает скилл, если запрос подходит
под его описание (изменения в нескольких файлах или на нескольких платформах, аудиты и исправление находок, релизы,
деплой, ревью). Если аргумент пуст, а в `.claude/plans/` есть план в работе, оркестратор продолжает этот план. Отвечает
он на вашем языке.

### Короткие команды

| Установка плагином | Ручная установка | Что вы получаете |
|---|---|---|
| `/orchestrator:status` | `/orchestrator status` | Сводка не длиннее 12 строк: прогресс плана (готово / в работе / осталось), что сейчас запущено, следующий шаг, решения, которых ждут от вас, режим лимитов и время сброса, расход относительно бюджета. |
| `/orchestrator:limits` | `/orchestrator limits` | Отчёт о лимитах в нескольких строках: режим, статус по моделям, заполнение контекста, время сброса и действия, которым последует оркестратор. |
| `/orchestrator:costs` | `/orchestrator costs` | Токены и доля лимита по ролям и по агентам, главные потребители, уровень бюджета плана и один совет, где сэкономить. |
| `/orchestrator:resume` | `/orchestrator resume` | Загружает чекпоинт плана в работе и продолжает; если такого плана нет, так и скажет. |
| `/orchestrator:setup` | `./install.sh --statusline` | Однократная настройка строки состояния. `/orchestrator:setup remove` её отменяет. |

Короткие команды запускаете вы сами; Claude их самостоятельно не вызывает.

## Жизненный цикл

### 0. Ворота лимитов

Первый шаг и повтор перед каждой волной агентов: `python3 scripts/limits.py` (около секунды, локально, только чтение).
Скрипт печатает `mode`, статус по моделям, заполнение контекста и список действий, которым затем следует оркестратор.
Хуки повторяют проверку сами, а `/orchestrator:limits` в любой момент показывает тот же отчёт. Подробнее —
[limits-and-context.md](limits-and-context.md).

### 1. Размер задачи

| Размер | Признаки | Что происходит |
|---|---|---|
| S | не больше 2 файлов, очевидная правка, без безопасности/прода/протокола | Оркестратор делает сам, без агентов. |
| M | 2–6 шагов, 1–2 области | Короткий план, 2–5 агентов, проверка. |
| L | несколько платформ или сервисов, протокол/крипто/безопасность, прод, пачка находок аудита, новая функция | Полный цикл; сначала план смотрит архитектор. |

### 2. Разведка (дёшево)

- Читается карта проекта `.claude/orchestrator/project-map.md`; если её нет, `orch-scout` (Haiku) строит её по
  `references/project-map-template.md` (структура, команды сборки и тестов, факты о проде, ловушки).
- Проверяются память и `.claude/plans/`.
- Scout возвращает карты `file:line — что`, по одной на область, параллельно. `orch-devops` может снять снимок прода в
  режиме «только чтение». Код оркестратор открывает сам лишь для приёмки результатов.

### 3. План

Ближайший [плейбук](#плейбуки) подсказывает состав ролей, порядок, проверки и примерный бюджет. Сам план — файл
`.claude/plans/YYYY-MM-DD-<slug>.md` по `templates/plan.md`. В шапке: статус (`in-progress`), время `Started:`,
`Budget:`, плейбук, размер и оценка токенов. У каждого шага — `file:lines`, маркер состояния (`[ ]` не начат, `[~]` в
работе, `[x]` готов — `/orchestrator:status` их считает), роль с моделью/усилием, зависимости, что идёт параллельно,
«готово, когда» и команда проверки. Ниже — гейт на прод, риски, раздел `## Checkpoint`, который держат актуальным, и
раздел `## Result`. Для задач L план сначала смотрит `orch-architect`, каждое расхождение разбирается явно. Вам
показывают сводку на 5–12 строк; дальше оркестратор идёт сам, если следующий шаг не необратим и не затрагивает прод.

### 4. Исполнение

- Каждый агент получает бриф по `templates/brief.md` — это единственный его контекст.
- Один писатель на файл; параллельные писатели в одном дереве сборки работают в отдельных git worktree.
- Фоновые агенты сообщают о завершении сами; оркестратор не угадывает их результат.
- Эскалация: сначала самая дешёвая подходящая модель; при неудаче — следующий уровень с тем же брифом и причиной
  неудачи.
- Долгую или независимую работу можно вынести в отдельный процесс с чистым контекстом (см.
  [Агенты с чистым контекстом](#агенты-с-чистым-контекстом)).

### 5. Проверка

Пропорциональна риску, на слово разработчику не верят:

- `orch-build-verifier` — всегда; `orch-reviewer` — на каждый шаг разработки.
- `orch-protocol-reviewer` — для крипто, auth, wire-форматов и совместимости; `orch-security` — для auth, периметра,
  rate limits и конфигурации прода; `orch-privacy-compliance` — когда персональные данные собирают, пишут в логи или
  передают дальше.
- `orch-qa` — для пользовательских сценариев; `orch-accessibility` — для интерфейса; `orch-test-engineer` — когда
  поведение изменилось без тестов; `orch-performance` — для горячих путей; `orch-dependency-auditor` — когда меняются
  зависимости.

Вердикт «на доработку» возвращается тому же разработчику через `SendMessage` (контекст сохраняется), затем
перепроверяются только исправления. Для критичных находок — панель опровержения из трёх независимых ревьюеров
(принимается при двух и более). См. [`references/verification.md`](../../skills/orchestrator/references/verification.md).

### 6. Гейт на прод

Деплой, перезапуск, правка конфигов и файрвола, `git push`, публикация, удаление, ротация секретов — ничего из этого не
происходит без вашего явного «да» на конкретный шаг в текущем разговоре, если сам запрос прямо не требует именно этого
действия. Порядок: снимок только для чтения → план с бэкапом и откатом → ваше «да» → бриф для `orch-devops` с
`OWNER_APPROVED: yes` и точным списком действий → проверки после изменения. См.
[`references/production-gate.md`](../../skills/orchestrator/references/production-gate.md).

### 7. Завершение

План получает статус `done` и раздел «Result» (сделано / не сделано и почему / чем проверено / что должен сделать
владелец / токены — фактический расход берётся из `costs.py --plan`). Устойчивые факты уходят в карту проекта и память.
Итоговый отчёт: что изменено, как проверено (команды → результаты), что осталось и какое решение нужно от вас.

## Состав команды: 27 ролей

Агентов зовут `orch-<role>`; при установке плагином обращаться к ним нужно как `orchestrator:orch-<role>`, список — в
`/agents`. `best` означает Fable, если он доступен вашему аккаунту, иначе Opus. Пометкой **новый** отмечены 12 ролей,
добавленных в 2.0 (15 ролей из 1.0 сохранили имена и настройки по умолчанию). У ролей «только чтение» в файлах агентов
отключены инструменты `Edit`, `Write` и `NotebookEdit`. Настройки по умолчанию лежат в `agents/orch-*.md`, полная
таблица с типовыми составами команд — в [`references/roles.md`](../../skills/orchestrator/references/roles.md).

### Руководство — планируют и решают

| Агент | Модель / усилие | Доступ | Для чего |
|---|---|---|---|
| `orch-architect` | best / high | только чтение | Ревью плана или спецификации для задач L, второе мнение, судья в спорных критичных вопросах. |
| `orch-analyst` | sonnet / high | только чтение | Расплывчатый запрос → требования и критерии приёмки; расхождения между документацией и кодом. |
| `orch-researcher` **новый** | sonnet / medium | только чтение, веб | Вопросы, для которых нужен веб: библиотеки, стандарты, прецеденты — ответ с источниками. |

### Разработка — пишут код

| Агент | Модель / усилие | Доступ | Для чего |
|---|---|---|---|
| `orch-dev-senior` | opus / high | код | Сквозные изменения, протоколы, конкурентность, правки в нескольких модулях. |
| `orch-dev-middle` | sonnet / medium | код | Чётко поставленная правка внутри одного модуля. |
| `orch-dev-junior` | haiku / medium | код | Точные диффы, переименования, механические правки. |
| `orch-frontend` **новый** | sonnet / medium | код | Веб-интерфейс: компоненты, состояние, формы, состояния «загрузка / пусто / ошибка», адаптивная вёрстка. |
| `orch-mobile` **новый** | opus / medium | код | iOS и Android: жизненный цикл, разрешения, защищённое хранилище, паритет платформ. |
| `orch-db-engineer` **новый** | opus / medium | миграции, запросы | Схемы, безопасные миграции с откатом, индексы, планы запросов. |
| `orch-api-designer` **новый** | sonnet / high | только файлы спецификаций | Контракты, модель ошибок, версионирование, совместимость — до написания кода. |
| `orch-designer` | opus / medium | стили, компоненты | Экраны, дизайн-токены, микротексты. |

### Качество — проверяют

| Агент | Модель / усилие | Доступ | Для чего |
|---|---|---|---|
| `orch-reviewer` | opus / high | только чтение | Состязательное ревью каждого шага разработки: пытается опровергнуть «готово», запускает сборку. |
| `orch-test-engineer` **новый** | sonnet / medium | только тесты | Недостающие тесты, пробелы в покрытии, нестабильные тесты, тестовые векторы. |
| `orch-qa` | sonnet / medium | только чтение | Сценарии, смоук-чеклисты, UX-ловушки, ложные обещания в интерфейсе. |
| `orch-performance` **новый** | opus / high | код | Измеримая оптимизация: профили, бенчмарки, N+1, утечки. |
| `orch-accessibility` **новый** | sonnet / medium | только чтение | WCAG 2.2 AA, скринридеры, контраст, клавиатура, масштабирование текста. |
| `orch-build-verifier` | haiku / low | только чтение | Запускает перечисленные команды, возвращает PASS/FAIL со строками ошибок. |

### Безопасность

| Агент | Модель / усилие | Доступ | Для чего |
|---|---|---|---|
| `orch-security` | best / high | только чтение | Модель угроз, аутентификация, периметр, rate limits; подтверждение или опровержение находок. |
| `orch-protocol-reviewer` | best / high | только чтение | Криптография, токены, wire-форматы, кросс-платформенная совместимость. |
| `orch-privacy-compliance` **новый** | sonnet / high | только чтение | Карта персональных данных, PII в логах, расхождения между политикой конфиденциальности и реальным поведением. |
| `orch-dependency-auditor` **новый** | sonnet / medium | только чтение | CVE с оценкой достижимости, устаревшие и заброшенные пакеты, лицензии. |

### Эксплуатация

| Агент | Модель / усилие | Доступ | Для чего |
|---|---|---|---|
| `orch-devops` | opus / medium | файлы инфраструктуры; прод — только при `OWNER_APPROVED: yes` | Снимки состояния, планы деплоя с откатом. |
| `orch-incident-responder` **новый** | opus / high | только чтение | Прод сломан: триаж, ранжированные гипотезы, самая дешёвая безопасная мера. |
| `orch-release-manager` **новый** | sonnet / medium | версия, changelog; публикует только с разрешения | Повышение версии по semver, release notes, чеклист релиза. |

### Поддержка

| Агент | Модель / усилие | Доступ | Для чего |
|---|---|---|---|
| `orch-scout` | haiku / low | только чтение | Карты `file:line`; навигация по огромным документам. |
| `orch-tech-writer` | sonnet / medium | документация | README, changelog, runbook'и — каждое утверждение сверяется с кодом. |
| `orch-toolsmith` | sonnet / medium | только чтение | Ищет и проверяет плагины, скиллы, MCP-серверы и LSP для предметной области; сам ничего не устанавливает. |

Если исчерпан лимит Fable, все роли `best` работают на Opus с усилием max; если исчерпан лимит Opus, senior-роли
переходят на Sonnet с усилием high (см. [Маршрутизация по моделям](limits-and-context.md#маршрутизация-по-моделям)).

## Плейбуки

Плейбук — готовый рецепт для типа задач: признаки, что он подходит, состав ролей с моделями, пронумерованные шаги, **гейт**,
который должен выполниться перед следующим шагом, способ проверки, примерный бюджет, типичные ловушки и пример запроса.
Оркестратор начинает план с ближайшего плейбука, выбрасывает неприменимые шаги (объясняя почему), а если подходят сразу
два — выстраивает их цепочкой, например incident → bugfix → release. Всего их двенадцать, полностью они описаны в
[`references/playbooks.md`](../../skills/orchestrator/references/playbooks.md); шаги с пометкой **[YES]** ждут вашего
явного «да». В таблице — типовая форма (∥ значит «параллельно»; порядок оркестратор подстраивает под задачу). Подсказка
по бюджету — примерная доля 5-часового лимита для задачи размера S, M или L: она попадает в строку `Budget:` плана, а
`costs.py --plan` после первой волны покажет реальную цифру.

| Плейбук | Когда применять | Типовой порядок | Подсказка по бюджету (S · M · L) |
|---|---|---|---|
| `bugfix` | Дефект с воспроизведением, стек-трейсом или падающим тестом; регрессия | scout (карта падающего пути) → test-engineer (сначала падающий регрессионный тест) → dev-middle или dev-senior, если баг затрагивает несколько модулей (минимальное исправление) → build-verifier ∥ reviewer | ≤ 2 · 2–6 · 8–15 % |
| `feature` | Новая видимая пользователю возможность, затрагивающая две области и больше | scouts ∥ → analyst (критерии приёмки) → architect ∥ api-designer → db-engineer (миграция + откат) → backend-разработчик ∥ frontend или mobile ∥ test-engineer → build-verifier → reviewer ∥ security и privacy-compliance (auth, персональные данные) ∥ accessibility (UI) → qa → tech-writer | ≤ 3 · 8–15 · 20–40 % |
| `refactor` | Перестройка кода без изменения поведения | scouts ∥ (вызывающие, публичная поверхность) → test-engineer (характеризационные тесты) → architect (L) → dev-senior малыми шагами, после каждого build-verifier → reviewer на весь diff → tech-writer (поправить пути в документации) | ≤ 3 · 5–12 · 15–30 % |
| `migration` | Изменение схемы БД, backfill, смена движка | scout ∥ db-engineer (только чтение) → architect (L) или db-engineer (expand → backfill → switch → contract) → db-engineer (миграция вперёд и откат, проверка на одноразовой БД) → dev (переходный код, тесты) → reviewer ∥ build-verifier → devops: снимок и план → **ваше «да»** → devops | ≤ 3 · 5–10 · 15–30 % |
| `dependency-upgrade` | Алерт по CVE, устаревшие мажорные версии, обновление рантайма | dependency-auditor (таблица по риску) → build-verifier (базовая линия) → researcher ∥ (breaking changes мажорных версий) → dev-middle по группам пакетов → test-engineer → reviewer → выкладка по обычному релизному пути с **вашим «да»** | ≤ 2 · 4–10 · 10–25 % |
| `security-audit` | Аудит, предрелизная проверка безопасности, модель угроз (только ваши системы, без разрушающих действий) | scouts ∥ (поверхность атаки) → security ∥ protocol-reviewer ∥ privacy-compliance ∥ dependency-auditor → дедупликация → панель опровержения для критичных → подтверждённые находки исправляются как баги → reviewer, второй раунд → tech-writer (что проверено, а что нет) | 3–6 · 8–15 · 25–50 % |
| `performance` | Медленный эндпоинт, страница, запрос или сборка; высокое потребление памяти | scout → performance (сначала базовая линия) → гипотезы ∥ test-engineer (фиксирующие тесты) → по одному изменению за раз (performance ∥ db-engineer) → build-verifier ∥ reviewer → performance (таблица «до/после») | ≤ 3 · 5–12 · 15–30 % |
| `incident` | Прод лежит или деградировал прямо сейчас | incident-responder ∥ devops (снимок) ∥ scout (недавние изменения) → варианты смягчения, у каждого свой откат → **ваше «да»** → devops → incident-responder (проверка восстановления) → исправление первопричины позже как bugfix → tech-writer (постмортем) | ≤ 2 · 3–8 · 10–20 % |
| `release` | Повышение версии, changelog, тег, публикация пакета или в магазине | release-manager (версия, changelog, заметки) → build-verifier (полная матрица) ∥ dependency-auditor → qa (смоук) → файлы версий ∥ документация → точные команды публикации и откат → **ваше «да»** → release-manager или devops | ≤ 2 · 3–8 · 8–15 % |
| `docs` | README, runbook, документация API; документация разошлась с кодом | scout → analyst (список расхождений) → tech-writer → build-verifier (запускает каждую описанную команду, проверяет ссылки) → reviewer (сверка утверждений с кодом) | ≤ 1 · 2–6 · 6–12 % |
| `test-coverage` | Низкое покрытие, регрессии без тестов, нестабильные тесты | build-verifier (базовая линия) → scout (непокрытые модули по убыванию риска) → test-engineer ∥ по модулям → охота на нестабильные тесты → build-verifier ∥ reviewer | ≤ 2 · 4–10 · 10–25 % |
| `onboarding` | Унаследованный или незнакомый репозиторий | build-verifier (ставится ли, собирается ли, тестируется ли, запускается ли?) → scouts ∥ по верхнеуровневым областям → analyst → architect (L) → tech-writer (карта проекта) | ≤ 1 · 2–5 · 5–12 % |

orch     > [limits] mode normal, fable ok, context 6%.

Отчёт

## Бюджет и расход

В шапке любого плана может стоять бюджет, например `**Budget:** 25%` (от 5-часового лимита) или `4M tokens`.
Оркестратор заполняет его при составлении плана, отталкиваясь от подсказки плейбука (см. [Плейбуки](#плейбуки)); если у
вас есть своя цифра, назовите её в запросе или поправьте строку сами в любой момент. Подсказки примерные, поэтому после
первой волны загляните в `costs.py --plan`. Расход считается по всем сессиям проекта с момента `Started:` плана.

- `/orchestrator:costs` показывает токены и долю лимита по ролям и агентам и положение дел с бюджетом.
- `/orchestrator:status` включает уровень бюджета в свою сводку.
- Хук обращается к оркестратору один раз при 80 % бюджета (предпочитать более дешёвые модели, обходиться без
  необязательных ревью) и один раз при 100 % (не запускать новых агентов, спросить вас, продлевать ли бюджет).

Синтаксис, точные сообщения и вопрос «проценты или токены» разобраны в разделе
[Бюджеты планов](limits-and-context.md#бюджеты-планов), сам отчёт — в разделе [Расходы](limits-and-context.md#расходы).

## Как продолжить работу

**После `/compact`, `/clear` или `claude --resume`.** Хук `SessionStart` плагина (matcher `compact|resume|clear`) находит
самый свежий план в `.claude/plans/*.md`, в шапке которого указано `in-progress`, и кладёт в новый контекст его шапку,
раздел `## Checkpoint` и однострочную сводку о лимитах. Если оркестратор сам не продолжил работу, наберите
`/orchestrator:resume`.

**После перезапуска.** В совсем новую сессию (`startup`) чекпоинт не подставляется. Наберите `/orchestrator:resume`:
команда загрузит чекпоинт плана в работе, сначала проверит лимиты и продолжит.

**После лимита.** В режиме `exhausted` оркестратор ничего не запускает, пишет чекпоинт и сообщает время сброса. После
сброса наберите `/orchestrator:resume`: упавших или завершённых агентов продолжают через `SendMessage`
(«Limit reset — continue from where you stopped and return the result in the agreed format.»), а не брифуют заново.

**Просьба о `/compact`.** Модель не может выполнить `/compact`. При 75 % контекста она записывает чекпоинт и просит вас
выполнить команду с подсказкой вида `/compact keep: plan <path>, running agents, next step`.

В хорошем чекпоинте (раздел шаблона) перечислено: что сделано, что в работе (id агента и что он делает), следующий шаг,
открытые решения и вопросы к вам, ключевые пути. Если правите план вручную, оставьте строку `**Status:** in-progress` в
первых 4000 символах — хук ищет её там (`checkpoint.py` понимает и русские слова «статус» и «чекпоинт»).

## Как писать хорошие брифы

Если вы брифуете агентов сами (или проверяете бриф оркестратора), берите `templates/brief.md`:

```
ROLE: orch-<role> · PLAN: .claude/plans/<file>.md, step <N>
GOAL: <одно предложение — что должно быть истинно после вашей работы>

CONTEXT (ready-made, do not search again):
- <file>:<A>-<B> — <что там> → read with `sed -n A,Bp <file>`

DO:
1. …

CONSTRAINTS:
- You may edit only: <files/dirs>. Everything else: report, do not touch.

DONE WHEN:
- <проверяемое утверждение>
- <негативный сценарий, который должен безопасно провалиться>

VERIFY (run yourself, attach output):
- `<команда>`

PRODUCTION: do not touch.
REPORT FORMAT: changes as `file:lines — what`, command outputs, deviations with reasons, what is not done.
```

Практические правила: давайте диапазоны (`file:A-B`), а не целые файлы; перечисляйте файлы, которые агент вправе
менять; формулируйте негативный сценарий; просите структурированный отчёт, а не прозу; разрешение на прод указывайте
явно (`PRODUCTION: do not touch` или `OWNER_APPROVED: yes — allowed exactly: …; rollback: …`). Шаблон брифа на
английском, и агенты читают его в таком виде; отвечать вам оркестратор будет на вашем языке.

## Параллельная работа

- Один писатель на файл. Большой контроллер или серверный файл правит один агент за раз.
- Разные файлы в одном скомпилированном дереве (один проект gradle/xcode/npm) всё равно могут ломать друг другу сборку.
  Второго писателя запускают с `isolation: "worktree"`; он коммитит в своей ветке и сообщает хеш. Оркестратор
  переносит изменения без коммита:

```bash
git cherry-pick -n <sha>
```

  Это работает на «грязном» дереве, если затронутые файлы там не изменены. Последующие правки — новые коммиты, они
  переносятся так же. Добавьте `.claude/worktrees/` в `.gitignore` репозитория.
- Не больше одной тяжёлой сборки каждого инструмента на дерево; для параллельных сборок Xcode — отдельные каталоги
  derived data.
- Лимиты параллелизма: `normal` — до 4 тяжёлых агентов, `economy` — до 2, `critical` — новых нет.
- Проверяйте, что новые исходники не попали в игнор молча (`git status --short --ignored <dir>`).

Подробности — в [`references/parallelism.md`](../../skills/orchestrator/references/parallelism.md).

## Агенты с чистым контекстом

Для долгой или независимой работы агента можно запустить в отдельном процессе `claude`, который не несёт историю
текущего чата. Оркестратор делает это сам, когда это уместно; можно и вручную:

```bash
S=~/.claude/skills/orchestrator/scripts        # ручная установка; при установке плагином скрипты лежат внутри каталога плагина

# бриф из файла, фоновый процесс
"$S/spawn.sh" orch-scout brief.md --mode headless --id scout-api

# бриф со стандартного ввода, с переопределением модели и усилия (например, пока Fable исчерпан)
echo "Review api/auth.py:10-120 ..." | "$S/spawn.sh" orch-reviewer - --model opus --effort max

# видимые режимы: terminal (macOS Terminal), tmux (сессия "orch"), interactive (macOS)
"$S/spawn.sh" orch-dev-middle brief.md --mode tmux

# состояние и результаты
"$S/collect.sh"                       # 20 последних запусков
"$S/collect.sh" scout-api --wait      # дождаться завершения запуска
"$S/collect.sh" scout-api --full      # полный результат вместо первых 60 строк
```

Параметры `spawn.sh`: `--mode headless|terminal|tmux|interactive` (по умолчанию `headless`), `--id`, `--model`,
`--effort`, `--max-turns` (по умолчанию 60), `--schema <file>`, `--perm acceptEdits|default|plan|auto|dontAsk|bypass`
(по умолчанию `acceptEdits`), `--cwd`. Переменные окружения: `ORCH_RUNS`, `ORCH_PERM`, `ORCH_WAIT_MAX`. Результаты
попадают в `<project>/.claude/runs/<run-id>/`. Режимам `terminal` и `interactive` нужен macOS Terminal, режиму `tmux` —
tmux. Переменные прокси и `ANTHROPIC_*` вашей оболочки передаются дочернему процессу через файл с правами `0600`,
который удаляется после старта. Запуски, сделанные так, учитывает `costs.py --project-wide`.

## Карта проекта

`.claude/orchestrator/project-map.md` (не больше примерно 150 строк) читается часто, поэтому короткая: что за проект,
компоненты и размеры, команды сборки/тестов/линтеров, полезные спецификации, факты о проде (только чтение), ловушки.
Первый раз её строит scout; оркестратор обновляет, когда она устаревает. Шаблон —
[`references/project-map-template.md`](../../skills/orchestrator/references/project-map-template.md). Коммитить её или
игнорировать — на ваше усмотрение. Секреты в неё класть нельзя: её читают часто и она может попасть в коммит.

## Где что лежит

| Путь | Что там |
|---|---|
| `.claude/plans/YYYY-MM-DD-<slug>.md` | Планы: шаги, чекпоинт, бюджет, результат. |
| `.claude/orchestrator/project-map.md` | Карта проекта. |
| `.claude/runs/<run-id>/` | Результаты запусков `spawn.sh`. |
| `.claude/worktrees/` | Git worktree параллельных писателей (добавьте в `.gitignore`). |
| `~/.claude/claude-orchestrator/` | Копия скриптов, снимок строки состояния, калибровка, ваш необязательный `limits.json`, состояние хуков. |

## Как не тратить лишнего

- Маленькие задачи оставляйте маленькими: S делается напрямую.
- Передавайте в брифах карты и диапазоны, чтобы дорогие агенты не искали сами.
- Лучше возобновить агента (`SendMessage`), чем брифовать нового.
- Сначала самая дешёвая подходящая модель; Fable/`best` — только для архитектуры, безопасности, протоколов и
  критичных решений.
- Просите компактные отчёты; не вставляйте большие файлы и полные diff в чат оркестратора.
- Поставьте строку состояния и следите за `ctx` — чекпоинт лучше сделать заранее, чем сжимать контекст в спешке.
- Режим `economy` — сигнал, а не помеха: он нужен, чтобы успеть закончить задачу до сброса окна.
- Ставьте `Budget:` на большие планы и на полпути смотрите `/orchestrator:costs`: главные роли показывают, куда уходит
  расход, а в конце отчёта идёт один совет по экономии (например, роль работает на более дорогой модели, чем требует её
  работа).
- Ориентировочная стоимость агента (из
  [`references/model-routing.md`](../../skills/orchestrator/references/model-routing.md)): scout 5–50k токенов,
  build-verifier 5–30k, junior 10–30k, middle 30–100k, senior 60–500k, reviewer 40–300k, architect/protocol/security
  60–300k. План из пяти шагов разработки с полной проверкой: 0.5–1.5M; кросс-платформенное изменение протокола с
  раундами ревью: 3–7M. Это порядки величин: суммы токенов в отчёте `costs.py` учитывают ещё и чтение кэша и получаются
  намного больше, поэтому сравнивайте роли между собой или смотрите колонки «≈ %».

## Рецепты

Что набрать → что произойдёт. Каждый рецепт работает и с `/orchestrator:orchestrator …`, и как обычный запрос словами.

### 1. Мелкая правка

```
/orchestrator:orchestrator переименуй ключ конфигурации retryCount в maxRetries в config.py и в единственном месте использования
```

Задача размера S: не больше двух файлов, очевидная правка, ни безопасности, ни прода. Оркестратор делает её сам — без
файла плана и без привлечения других агентов.

### 2. Баг с регрессионным тестом

```
/orchestrator:orchestrator после выхода из аккаунта кука сессии остаётся в браузере — найди причину, исправь и добавь регрессионный тест
```

Размер M, плейбук `bugfix`. Scout находит падающий путь, воспроизведение и команды тестов; если воспроизвести сбой не
удаётся, оркестратор спросит вас, а не будет гадать. `orch-test-engineer` сначала пишет регрессионный тест и убеждается,
что он падает по названной причине. `orch-dev-middle` — или `orch-dev-senior`, если баг затрагивает несколько
модулей, — делает минимальное исправление. Затем `orch-build-verifier` и `orch-reviewer` проверяют его параллельно;
вердикт «на доработку» возвращается тому же разработчику.

### 3. Новая функция с бюджетом

```
/orchestrator:orchestrator добавь сброс пароля: API-эндпоинт, миграцию и веб-страницу. Уложись в 25% 5-часового лимита. На прод не выкатывай.
```

Размер L, плейбук `feature`. Scouts картируют области, `orch-analyst` превращает запрос в критерии приёмки (вопросы,
ответить на которые можете только вы, задаются сразу), `orch-architect` и `orch-api-designer` фиксируют дизайн и
контракт до написания кода, а `orch-db-engineer` пишет миграцию с откатом. Затем backend-разработчик, `orch-frontend` и
`orch-test-engineer` работают параллельно над разными файлами (в git worktree, если у них общее дерево сборки). Проверяют
`orch-reviewer`, `orch-security` и `orch-privacy-compliance` (функция касается аутентификации и персональных данных),
`orch-accessibility` и `orch-qa`; завершает `orch-tech-writer`. В шапке плана появится `Budget: 25%`: при 80 % хук
напомнит оркестратору выбирать более дешёвые варианты, при 100 % — не запускать новых агентов и спросить вас. Просьба
не выкатывать на прод останавливает план перед шагом с продом.

### 4. Аудит безопасности

```
Используй оркестратор: проведи аудит кода аутентификации и загрузки файлов в этом API; нужны только подтверждённые находки, с file:line и способом исправления
```

Плейбук `security-audit` (только ваши системы, без разрушающих действий). Сначала scouts картируют поверхность атаки. Затем
`orch-security`, `orch-protocol-reviewer`, `orch-privacy-compliance` и `orch-dependency-auditor` берут по одной линзе и ничего
не меняют (в режиме `economy` — по два за раз). Оркестратор убирает дубли и ранжирует находки; критичные идут на панель
опровержения из трёх ревьюеров (принимается при двух и более), подтверждённые становятся шагами bugfix, каждый из которых
перепроверяется вторым раундом. В отчёте сказано, что проверено, а что нет. Запросы к развёрнутой системе и правки
конфигурации ждут вашего «да».

### 5. Обновление зависимостей

```
/orchestrator:orchestrator исправь все находки npm audit, достижимые из нашего кода, а потом подними React до последней мажорной версии
```

Плейбук `dependency-upgrade`. `orch-dependency-auditor` строит таблицу, упорядоченную по риску и трудоёмкости (пакет,
текущая версия, целевая, серьёзность, достижимость, действие); `orch-build-verifier` фиксирует базовую линию на нетронутом
дереве; `orch-researcher` читает changelog мажорных версий и прикладывает источники. Потом `orch-dev-middle` идёт по
группам — сначала патчи и минорные версии, затем по одной мажорной за шаг — с проверкой сборки после каждого шага,
`orch-test-engineer` покрывает поведение, которое обновление показало непротестированным, а `orch-reviewer` проверяет
diff lock-файла. Выкладка идёт обычным релизным путём и требует вашего «да».

### 6. Авария на проде

```
Оформление заказа отдаёт 502 с 14:20. Выясни причину и предложи самое безопасное исправление; перед любыми изменениями на сервере спроси меня
```

Плейбук `incident`. `orch-incident-responder` проводит триаж — что отказывает, с какого момента, у кого, что менялось, —
пока `orch-devops` снимает снимок только для чтения, а scout перечисляет недавние изменения. Они предлагают варианты
смягчения, сначала самый дешёвый и безопасный, у каждого свой откат, и оркестратор останавливается и ждёт вашего явного
«да». Только после этого `orch-devops` получает бриф с `OWNER_APPROVED: yes` и точным списком действий; всё лишнее,
например второй перезапуск, снова останавливается и спрашивает. Responder проверяет восстановление, исправление
первопричины приходит позже как bugfix, а `orch-tech-writer` готовит постмортем без поиска виноватых.

### 7. Незнакомая кодовая база

```
Мне достался этот репозиторий. Объясни, что он делает, как его запустить и что в нём рискованно. Ничего не меняй.
```

Плейбук `onboarding`. Сначала `orch-build-verifier` проверяет, ставится ли проект, собирается ли, проходят ли тесты и
запускается ли, фиксирует PASS или FAIL и ничего не чинит. Scouts параллельно картируют каждую верхнеуровневую область;
`orch-analyst` перечисляет расхождения между документацией и кодом, рискованные места и открытые вопросы;
`orch-tech-writer` пишет `.claude/orchestrator/project-map.md` (не больше примерно 150 строк) по командам, которые
действительно запускали, — с неё начинается каждая следующая задача.

### 8. Вернуться к работе

```
/orchestrator:status
/orchestrator:costs
/orchestrator:resume
```

`status` показывает, где находится план и что запущено; `costs` — сколько это стоило и как обстоят дела с бюджетом;
`resume` после `/compact`, `/clear`, перезапуска или сброса лимита загружает чекпоинт и продолжает работу, возобновляя
завершённых или упавших агентов через `SendMessage` вместо нового брифинга.

## Обновление и удаление

**Обновление.** В Claude Code: `/plugin marketplace update claude-orchestrator`, затем
`/plugin update orchestrator@claude-orchestrator` (или через меню `/plugin`). Из терминала:
`claude plugin update orchestrator@claude-orchestrator`. Ручная установка: `git pull && ./install.sh` с теми же флагами.

**Удаление.** Сначала наберите `/orchestrator:setup remove` — команда уберёт запись строки состояния, вернёт вашу прежнюю
строку (данные и `limits.json` остаются в `~/.claude/claude-orchestrator`; для полной очистки удалите эту папку вручную).
Затем
`/plugin uninstall orchestrator@claude-orchestrator` (из терминала:
`claude plugin uninstall orchestrator@claude-orchestrator`). При желании — ещё `/plugin marketplace remove claude-orchestrator`.
Если первый шаг забыли, удалите запись `statusLine` в `~/.claude/settings.json` (резервная копия была сделана при
настройке) или запустите `./uninstall.sh` из клона репозитория. Ручная установка: `./uninstall.sh` (или
`./uninstall.sh --project <dir>`) удаляет скилл, агентов `orch-*`, `~/.claude/claude-orchestrator` и только наши записи
строки состояния и хуков, а прежнюю строку состояния возвращает.

## Переход с v1

Версия 2.0.0 сменила название продукта, поэтому имена изменились повсюду:

| | v1 | 2.0 |
|---|---|---|
| Продукт | Team Orchestrator | Claude Orchestrator |
| Плагин | `team-orchestrator` | `orchestrator` |
| Маркетплейс | `team-orchestrator` | `claude-orchestrator` |
| Главная команда | `/team-orchestrator` (`/team-orchestrator:team-orchestrator`) | `/orchestrator:orchestrator` (ручная установка: `/orchestrator`) |
| Короткие команды | `/team-orchestrator resume` | `/orchestrator:status`, `:limits`, `:costs`, `:resume`, `:setup` |
| Агенты | 15, `team-orchestrator:orch-<role>` | 27, `orchestrator:orch-<role>` |
| Каталог данных | `~/.claude/team-orchestrator/` | `~/.claude/claude-orchestrator/` |

**Установка плагином.**

```
/plugin uninstall team-orchestrator@team-orchestrator
/plugin marketplace remove team-orchestrator
/plugin install orchestrator --marketplace newzealandgrom/claude-orchestrator
```

Если вы включали строку состояния, наберите `/orchestrator:setup` ещё раз: она переключит `settings.json` на новый
каталог и сохранит вашу собственную строку состояния, которая выводилась после старой.

**Ручная установка.** Обновите репозиторий и запустите `./install.sh` с теми же флагами, что и раньше. Он удалит старую
папку `skills/team-orchestrator` и, если в `settings.json` остались записи строки состояния или хуков v1, автоматически
переведёт их на новую версию (перед этим делается резервная копия, а ваша собственная строка состояния сохраняется). `./uninstall.sh`
новой версии убирает и остатки v1.

**Данные.** Ваши планы в `.claude/plans/` и карта проекта `.claude/orchestrator/project-map.md` продолжают работать как
есть. Новые скрипты читают старые `limits.json` и снимок строки состояния из `~/.claude/team-orchestrator/` как запасной
источник, но пишут только в `~/.claude/claude-orchestrator/`; калибровка начинается с нуля. Когда закончите, скопируйте
нужный `limits.json` в новый каталог, а старый каталог удалите. Подробнее — в разделе
[Переход с v1](limits-and-context.md#переход-с-v1).

## Если что-то не так

**Команды `/orchestrator:…` не находятся.** Наберите `/reload-plugins` или перезапустите Claude Code, затем проверьте
`/plugin` → «Installed». На Claude Code версии ниже 2.1.275 однострочная установка не сработает — используйте двухшаговую
форму из раздела [Установка](#установка).

**`/agents` показывает меньше 27 агентов.** Установлена старая версия; обновите её (см.
[Обновление и удаление](#обновление-и-удаление)).

**Оркестратор сделал задачу один, без привлечения агентов.** Задача получила размер S (не больше двух файлов, очевидная правка, без
безопасности, протокола и прода). Так и задумано.

**Нет `5h` / `7d` в строке состояния или строки состояния нет вовсе.** См. раздел
[Если что-то не так](limits-and-context.md#если-что-то-не-так) в руководстве по лимитам.
